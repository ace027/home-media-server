<objective>
Adapt Phase 1 to the owner's hardware change: the media `/data` storage will be an **existing ZFS pool on SSDs** that already holds a media library to keep. The pool will be moved from an old server, which is still running and can `zpool export`, into a fresh Proxmox install.

Purpose: import safely without data loss, consolidate into one hardlink-safe `<pool>/data` dataset, fix ownership, and point the VM at the real mountpoint.
Output: new `scripts/host/05-import-pool.sh`; fixes to `00-zfs-datasets.sh`, `20-create-vm.sh` and the stubs; CI step; runbook section; architecture note.
</objective>

    1. **Import.** If `zpool list -H -o name "$POOL"` succeeds, log `pool $POOL already imported` and skip. Otherwise:
       - Capture `zpool import 2>&1 || true`.
       - If the output has no line matching `^[[:space:]]*pool: $SOURCE_POOL$`, die: "pool $SOURCE_POOL not found among importable pools. On the old server run 'zpool export $SOURCE_POOL' before moving the drives, then check the disks are detected (lsblk)".

    2. **Inventory** (read-only, logged). Run `zfs list -H -r -o name,used,avail,mountpoint,recordsize "$POOL"`, then log a WARN: "do not run 'zpool upgrade $POOL' until you are sure you won't move the pool back to the old server".

         - It must have no children. If it does, die and point to runbook 1a, "multiple datasets".
         - Then `run zfs rename "$MEDIA_DATASET" "$POOL/data"`.
       - Else: log the depth-1 datasets (excluding `$POOL/backups`) with their `used` values. Log guidance: "set MEDIA_DATASET=<pool>/<dataset> to rename your main media dataset to $POOL/data, or leave unset to have 00-zfs-datasets.sh create an empty one; see runbook section 1a".

         - If `FIX_OWNERSHIP=1`: `run chown -R "$PUID:$PGID" "$mnt"` and `run chmod -R u=rwX,g=rwX,o=rX "$mnt"`.

       - Otherwise log `ownership OK`.

  1. **Before moving the drives** (old server):
     - Stop anything using the pool.
     - `zpool status <pool>` must be healthy.
     - Record `zfs list -r -o name,used,avail,mountpoint,recordsize <pool>`.
     - `zpool export <pool>`.
     - Expected output: the pool disappears from `zpool list`.

Explain renaming to `tank` versus keeping the name with `POOL=<name>` everywhere. Explain `FORCE_IMPORT=1` and when it's safe.
  3. **Do not `zpool upgrade`** until you're committed to the new server.
  4. **Consolidation decision tree.** Hardlinks need downloads and media in one dataset.
     - (a) All media is in one dataset with no children: `MEDIA_DATASET=<pool>/<ds> ... --apply` renames it to `<pool>/data`. This is instant and uses no extra space.
     - (b) Media is split across several datasets: rename the largest to `data` as in (a).

       - Only then destroy the source dataset, with `zfs destroy <pool>/<ds>` after an explicit snapshot, or keep the snapshot until the library is confirmed in Phase 2.

Existing `movies` → `media/movies`, 4K titles → `media/movies-4k`, anime → `media/anime-tv`/`anime-movies`, music → `media/music`. Phase 2 imports them into Sonarr/Radarr/Lidarr as an existing library, with no re-downloads.

  7. Continue with section 2. `00-zfs-datasets.sh` sets the properties on the existing dataset.
